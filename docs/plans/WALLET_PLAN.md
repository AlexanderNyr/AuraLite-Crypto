# WALLET_PLAN — keys, signing, wallet, ceremony

**Status:** 📋 PLAN (W0–W7)  
**Stage:** Stage 1: W0–W4. ⏸ Stage 2: W5–W7 (hardware keys, web wallet, genesis ceremony).  
**Deliverable:** `patches/0059-W0-...` … `patches/0066-W7-...`
**Dependencies:** CORE C1–C4 (addresses/signatures), NODE D4 (RPC).

## Problem

"A private key in a text file" is the most common reason funds are lost. We need
a real keystore, offline signing, multisig for the treasury and a transparent
procedure for generating genesis keys.

## Decisions

- **D-W1.** BIP-39 (mnemonic) → BIP-32/44 derivation path `m/44'/ALCRY'/0'/0/i`.
- **D-W2.** Keystore: Argon2id + AES-256-GCM + scrypt parameters in the file; keys zeroized; never write a private key to logs.
- **D-W3.** Offline signing as a first-class scenario: `unsigned tx` → QR/file → `signed tx` → broadcast.
- **D-W4.** Treasury and validators — only M-of-N multisig, never one key.

## Phases

| Phase | Title | DoD | Test gate |
|---|---|---|---|
| **W0** | Baseline | audit of "where keys could end up" + threat notes | NC: key in a log → gate red (tree search) |
| **W1** | Crypto keystore | BIP-39/32/44, encryption, zeroize, versioned format | BIP-32 test vectors; 1000 wrong passwords → 0 decryptions; format fuzz |
| **W2** | `aura-wallet` CLI | `new/import/list/balance/transfer/sign/broadcast/stake/vote` | 40 CLI vectors, including rejection of a tx with a foreign chain-id |
| **W3** | Offline signing | unsigned/signed tx format, QR/USB, verification on the online machine | air-gapped scenario end-to-end; NC: signature with a foreign domain → reject |
| **W4** | Multisig | M-of-N contract, signature collection, timeouts, member rotation | 3-of-5: 3 collected → success, 2 → reject; NC: threshold bypass → red |
| ⏸ **W5** | Hardware keys | HID/CCID-like device protocol, on-screen confirmation | 10 "human confirmed/denied" scenarios; NC: blind confirmation → red |
| ⏸ **W6** | Web/browser wallet | WASM build of `aura-keys`, extension, deep links, phishing protection | signing shows the human the **real** tx fields; NC: recipient substitution in UI → red |
| ⏸ **W7** | Genesis ceremony | offline generation, Shamir sharing, witness logs, destruction of temporary media | O5: not one private key in the repository/CI; pubkey set matches genesis hash |

**Note on Stage 1:** testnet genesis keys are generated by a simplified but
documented procedure in O4 (no value, no HSM). The full W7 ceremony belongs to
mainnet and ⏸ Stage 2.

## Risks

- Phishing/address substitution in the UI — W6 + `chain_id` check + human-readable amount.
- Lost mnemonic — UX warnings, but **no** "recovery by email".
- One person holding the treasury key — W4/W7.

## Non-goals

Custodial service, KYC, exchange integrations, a mobile app (possible separate
plan after M4).

## Closure criteria

A user can create a key, sign a tx on an offline machine and broadcast it; the
treasury and validators are protected by multisig; genesis keys were generated
by a documented ceremony.
